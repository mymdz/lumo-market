# Lumo Market: подробное описание

[English version](../en/overview.md) · [Схема БД](database.md) · [README](../../README.md)

Симулятор европейского маркетплейса **Lumo Market**, который непрерывно пишет
свою активность в PostgreSQL. Нужен как «живой» OLTP-источник для экспериментов
с lakehouse, CDC, инкрементальными загрузками и BI.

- ~20 000+ товаров (растёт), 390 листовых категорий в 17 департаментах, ~360 брендов
- собственный склад (1P) + сотни сторонних продавцов (3P), fulfilment by Lumo
- 15 стран, 6 валют (EUR, PLN, CZK, SEK, DKK, **MDL**), НДС по странам
- 2 года истории генерируются за минуты, потом симуляция идёт в реальном времени
- 5 000 → 13 000 заказов в день + сезонность, распродажи, инциденты, шум

## Быстрый старт

```bash
docker compose up -d --build
# следить за прогрессом
docker compose logs -f simulator
curl localhost:8088/status
```

Postgres доступен на `localhost:5433` (`lumo` / `lumo`, база `lumo`).
Бизнес-данные лежат в схеме `shop`, служебное состояние симулятора в схеме `sim`.

Сначала симулятор генерирует историю (`history_days`, по умолчанию 730): полный
backfill занимает около 12 минут. Затем он создаёт индексы и FK и переходит в
live-режим: заказы появляются в реальном времени.

Локально без Docker (нужен только Postgres):

```bash
go run ./cmd/lumo -config config.yaml run
go run ./cmd/lumo -config config.yaml reset   # удалить все данные
```

Для быстрого пробного запуска: `LUMO_HISTORY_DAYS=30 LUMO_INITIAL_PRODUCTS=5000`.

Ресурсы на дефолтных настройках (2 года, 5k→13k заказов/день): база около 17–20 ГБ,
процесс симулятора держит мир в памяти, пик около 2.6 ГБ RAM. Меньше истории
означает пропорционально меньше и того, и другого.

Порты можно поменять переменными `LUMO_PG_PORT` (по умолчанию 5433) и
`LUMO_API_PORT` (по умолчанию 8088).

Настройки читаются слоями, каждый следующий перекрывает предыдущий: встроенные
значения по умолчанию → `config.yaml` (в гите) → `config.local.yaml` рядом с ним
(необязательный, в `.gitignore`, только ключи, которые нужно поменять; пример в
`config.local.example.yaml`) → переменные окружения `LUMO_<NAME>`, например
`LUMO_DIRT_LEVEL=0`. Это работает и в Docker (каталог проекта смонтирован в
контейнер только для чтения), и при запуске бинарника напрямую.

## Время, простои и даты

```bash
curl localhost:8088/status                # фаза, время, заказы по дням, активные события
curl localhost:8088/stats                 # примерные размеры таблиц
curl -XPOST 'localhost:8088/speed?x=0.5'  # замедлить (симуляция начнёт отставать от реального времени)
curl -XPOST localhost:8088/pause
curl -XPOST localhost:8088/resume
curl -XPOST localhost:8088/resync         # скорость 1 и догнать реальное время
go run ./cmd/lumo check              # найти строки, датированные будущим
```

**Простой.** Генератор можно выключить хоть на неделю: при следующем старте он
восстановит мир из БД и на максимальной скорости досимулирует пропущенный период
(заказы, доставки, возвраты, закупки, кампании — всё, что должно было случиться),
затем продолжит в реальном времени. Неделя при ~13k заказов/день догоняется
примерно за 30 секунд. Всё, что досимулировано, пишется обычными INSERT/UPDATE с
историческими timestamps, поэтому для CDC это выглядит как пачка изменений в
момент старта. Пауза и замедление работают так же: после `resume`/`resync`
пропущенное время досчитывается.

**Будущее.** Ни одно событие не датируется позже текущего момента: время
симуляции никогда не обгоняет реальное. Ускорение (`speed > 1`) возможно только
с `allow_future: true`, тогда данные сознательно уходят в будущее. Если потом
выключить `allow_future`, симулятор подождёт, пока реальное время его догонит.

Будущими легитимно бывают только **плановые** колонки: `shipments.promised_at`
(обещанная дата доставки), `purchase_orders.expected_at` (ожидаемая поставка),
`campaigns.starts_at/ends_at` (кампании заводятся за 3–6 недель до старта),
`coupons.valid_from/valid_to`. А `returns.received_at` намеренно хранится в
местном времени склада без часового пояса, поэтому в UTC он выглядит на 1–2 часа
«впереди». `lumo check` это учитывает и проверяет все остальные колонки.

- Рестарты безопасны: всё состояние (включая заказы «в полёте») хранится в БД,
  каждая контрольная точка пишется одной транзакцией.
- Если упасть во время первичного backfill истории, он начнётся заново.

## Схема `shop`

| Область | Таблицы |
|---|---|
| Справочники | `currencies`, `countries`, `fx_rates`, `warehouses`, `categories` (дерево), `brands` |
| Каталог | `products`, `product_variants` (SKU/EAN, размер/цвет/память), `offers` (цена продавца), `price_history` |
| Маркетплейс | `sellers` (1P + 3P, статусы onboarding/active/suspended/closed) |
| Склад | `stock_levels`, `stock_movements`, `suppliers`, `purchase_orders`, `purchase_order_items` |
| Клиенты | `customers`, `addresses` |
| Маркетинг | `campaigns`, `coupons` |
| Продажи | `carts`, `cart_items`, `orders`, `order_items`, `order_status_history`, `payments`, `refunds`, `shipments`, `returns`, `reviews` |

Суммы в заказах хранятся в валюте заказа (`orders.currency`), `orders.fx_rate`
показывает сколько единиц валюты за 1 EUR в день заказа. Цены офферов в EUR.

Все колонки, их смысл и возможные значения описаны в [database.md](database.md).
Примеры запросов: [`examples/queries.sql`](../../examples/queries.sql).

## Что делает данные «живыми»

**Спрос.** Сессии приходят как неоднородный пуассоновский процесс по каждой стране:
суточный профиль в локальном часовом поясе, дни недели, месяцы, национальные
праздники (включая православную Пасху в Молдове), дни зарплаты, AR(1)-шум.
Возвращающиеся клиенты выбираются пропорционально их активности, новых приводит
«маркетинг», бюджет которого каждый день подстраивается под целевой рост по каждой
стране отдельно.

**Календарь.** Winter Sale, Valentine's, Easter, Mother's Day, чемпионат по футболу
(чётные годы), Lumo Days (июльская мега-распродажа), Summer Sale, Back to School,
Halloween, Singles Day, Black Friday Week (с пиком ×2.3 в пятницу), Christmas с
дедлайном доставки и провалом 24–25 декабря, After-Christmas Sale, недели брендов,
коллаборации с инфлюенсерами (промокоды вида `ANNA15`). Погодные волны: жара
(вентиляторы, кондиционеры, купальники ×3–4) и холод (обогреватели, пуховики).

**Каталог.** Популярность товаров распределена с тяжёлым хвостом: топ-1% товаров
даёт ~20% выручки, топ-20% даёт ~80%, у многих товаров продаж почти нет. У товаров
есть жизненный цикл (рост, плато, спад, снятие с продажи и распродажа остатков),
у техники выходят новые поколения («Nova 12 Pro» → «Nova 13 Pro»). Спрос реагирует
на цену (эластичность), рейтинг отзывов, наличие на складе и вирусные всплески.

**Покупатели.** 7 сегментов (bargain hunters, loyal premium, families, fashionistas...),
предпочтения по департаментам зависят от пола, возраста, детей и питомцев.
Корзины бросают (~65%), часть возвращается после письма. Расходники покупают
повторно по циклу. Клиенты уходят (есть «одноразовые»), плохой опыт (опоздание,
отмена продавцом, потерянная посылка, товар с плохим рейтингом) ускоряет уход.
Раз в месяц пересчитываются уровни лояльности, раз в месяц идёт win-back.

**Заказ.** Оплата с отказами по методам (карты ~5%, Klarna ~8%), повторы, отмена
неоплаченных, антифрод, авторизация→capture при отгрузке, наложенный платёж с
отказами на пороге. Склад работает с cut-off 14:00 и не работает в воскресенье,
в пики бэклог. Сторонние продавцы отгружают медленнее и иногда отменяют. Перевозчики
страны со своей скоростью, опозданиями и потерями. Возвраты в 14-дневный срок ЕС
(одежда ~30%, электроника ~5%, «bracketing» — заказ двух размеров), отзывы на
разных языках с рейтингом, зависящим от качества товара и доставки.

**Бизнес-события во времени.** Запуск рынков (PT/IE, PL, CZ, северные страны,
Молдова) и складов (Poznań, Zaragoza — после открытия сроки доставки в регион
падают), онбординг, приостановка и уход продавцов, закупки у поставщиков со
сроками поставки и срывами, дефициты и потерянный спрос.

**Инциденты.** Падения платёжных провайдеров, сайта, деградация в Black Friday,
забастовки перевозчиков, задержки склада, баг цены (товар за 1–10% цены →
всплеск заказов → массовая отмена), бот-атаки на корзины, падение Android-приложения.
Активные события видны в `/status`.

## Грязь (`dirt_level`, 0..1)

- дубли клиентов (тот же человек с другим email), тестовые аккаунты `@lumomarket.test`
- email с пробелами/заглавными, телефоны в 5 форматах, города в разных написаниях
  (`München`/`Munich`/`Muenchen`, `Chișinău`/`Chisinau`/`Кишинёв`), индексы без
  ведущего нуля, NL-индексы без пробела, Eircode без значения
- описания NULL или в HTML, двойные пробелы в названиях, товары без бренда
- оверселл: отрицательные остатки, отмены продавцом
- **late-arriving данные**: платежи, появляющиеся в БД с `created_at` в прошлом
- **окна «багов»**: в течение нескольких часов/дней конкретная таблица обновляется
  без изменения `updated_at` (ловушка для инкрементальной загрузки по `updated_at`)
- дубли строк в `order_status_history`
- `order_items` вообще без `updated_at` (статусы меняются, видно только через CDC)
- `returns.received_at` в локальном времени склада без часового пояса
- hard delete: корзины старше 30 дней удаляются ежедневно
- GDPR: анонимизация клиентов и их адресов
- редкие рассинхроны `orders.grand_total` на 1 цент

## Эволюция схемы

Миграции применяются в симулированный момент времени (строки до миграции имеют NULL):

| Миграция | Когда | Что |
|---|---|---|
| `m001_shipments_co2` | −580 дней | `shipments.co2_grams` |
| `m002_orders_utm` | −470 дней | `orders.utm_source`, `utm_campaign` |
| `m003_products_eco_score` | −310 дней | `products.eco_score` (+ массовый backfill через 2 месяца) |
| `m004_order_items_gift_wrap` | −130 дней | `order_items.gift_wrap NOT NULL DEFAULT false` |
| `m005_customers_phone_verified` | **+14 дней** | `customers.phone_verified_at` (в live-режиме) |
| `m006_reviews_media` | **+45 дней** | `reviews.media_count` (в live-режиме) |

Отсчёт от момента первого запуска. Список в [`internal/app/migrations.go`](../../internal/app/migrations.go).

## CDC

Postgres запущен с `wal_level=logical` и `track_commit_timestamp=on`, так что
Debezium / logical replication подключаются сразу.

## Архитектура (hexagonal)

```
cmd/lumo                 wiring
internal/domain          сущности и справочные спецификации (без зависимостей)
internal/ports           Store, ReferenceData (driven), Control (driving)
internal/app             ядро: движок дискретно-событийной симуляции, модели поведения
internal/adapters/
  postgres               COPY-загрузка, пакетные UPDATE через temp tables, снапшот для рестарта
  refdata                встроенные YAML-справочники (категории, бренды, страны, имена, тексты)
  httpapi                управление временем
  config                 YAML + переменные окружения LUMO_*
```

Ядро — дискретно-событийная симуляция с собственными часами. Заказы, корзины и
закупки — агрегаты со своим следующим шагом в очереди событий. Во время backfill
агрегаты пишутся один раз, когда их жизненный цикл завершён (быстро, без UPDATE),
в live-режиме каждое изменение пишется как настоящий INSERT/UPDATE.

Тесты: `go test ./...`; интеграционный тест простоя против настоящего Postgres
(создаёт и удаляет отдельную БД, проверяет догоняние недели и отсутствие будущих дат):

```bash
LUMO_TEST_DSN='postgres://lumo:lumo@localhost:5433/lumo?sslmode=disable' \
  go test -tags integration -v -timeout 60m ./internal/integration/
```

Справочники лежат в `internal/adapters/refdata/data/*.yaml`: категории, шаблоны
названий, бренды, города, имена можно править без изменения кода.
